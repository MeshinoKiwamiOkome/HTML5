🌐 HTTP・HTTPSプロトコル 学習サンプル

WebブラウザとWebサーバーの間の通信を担う HTTP・HTTPS プロトコルの 仕組み・メッセージ構造・メソッド・ステータスコード・HTTP/2 を学びましょう。

① HTTPプロトコルとは

重要ポイント：HTTPはWebブラウザとWebサーバーの間でデータをやり取りするプロトコルである
HTTP（HyperText Transfer Protocol）は、 WebブラウザがWebサーバーにリソースを要求（リクエスト）し、 サーバーが応答（レスポンス）を返すためのアプリケーション層のプロトコルです。 ステートレス（状態を保持しない）な設計で、 各リクエストは独立して処理されます。

HTTP のバージョン比較

バージョン主な特徴接続方式
HTTP/1.0 リクエストごとにTCP接続を確立・切断 都度接続（非持続接続）
HTTP/1.1 持続接続（Keep-Alive）・パイプライン化 持続接続（デフォルト）
HTTP/2 TCP接続を共有・リクエストの多重化・ヘッダー圧縮・サーバープッシュ 多重化（1つのTCP接続で並列処理）
HTTP/3 TCPではなくUDP上のQUICプロトコルを使用 QUIC（UDP）

② HTTPSプロトコル

重要ポイント：HTTPSはHTTPにTLS/SSLによる暗号化を加えたセキュアなプロトコルである
HTTPS（HTTP Secure）は、HTTP通信を TLS（Transport Layer Security）または SSL（Secure Sockets Layer）で暗号化したプロトコルです。 通信内容の盗聴・改ざん・なりすましを防止します。 現代のWebでは標準的に使用され、ブラウザは HTTP サイトに「保護されていない通信」と表示します。

HTTP vs HTTPS の比較

盗聴対策なしあり
改ざん検知なしあり
サーバー認証なしSSL証明書で認証
SEO不利有利（Googleが優遇）
必須の場面—Geolocation / getUserMedia / Service Worker 等

・SSL証明書はサーバーの正当性を証明する

③ HTTPのメッセージ構造

重要ポイント：HTTPメッセージはスタートライン・ヘッダー・空行・ボディの4つで構成される
HTTPのリクエスト・レスポンスはどちらも同じ基本構造を持ちます。 スタートライン（リクエストライン or ステータスライン）・ ヘッダーフィールド・空行・メッセージボディ の順で構成されます。

リクエストメッセージの構造

POST /api/users HTTP/1.1 ← リクエストライン（メソッド・URI・バージョン）
Host: www.example.com ← ヘッダーフィールド
Content-Type: application/json
Content-Length: 27
Authorization: Bearer eyJhbGci...
← 空行（ヘッダーとボディの区切り）
{"name":"Alice","age":30} ← メッセージボディ

レスポンスメッセージの構造

HTTP/1.1 200 OK ← ステータスライン（バージョン・ステータスコード・フレーズ）
Content-Type: application/json; charset=UTF-8 ← ヘッダーフィールド
Content-Length: 45
Cache-Control: max-age=3600
Set-Cookie: session=abc123; HttpOnly; Secure
← 空行
{"id":1,"name":"Alice","age":30} ← メッセージボディ

④ HTTPのリクエストメソッド（8種類）

重要ポイント②：HTTPのリクエストメッセージで利用可能なメソッドには、GET・POSTなど8種類ある
HTTPメソッドはリクエストの目的・操作の種類を示します。 HTTP/1.1 では GET・POST・PUT・DELETE・HEAD・OPTIONS・PATCH・TRACE・CONNECT が定義されています。 試験では特に GET・POST・PUT・DELETE・HEAD・OPTIONS の違いが重要です。
GET
リソースの取得。ボディなし。 URLにパラメータを付与（クエリ文字列）。 べき等・安全
POST
リソースの新規作成・データ送信。 ボディにデータを含む。 べき等でない
PUT
リソースの置き換え（全体更新）。 指定URIにリソースを作成または完全置換。 べき等
PATCH
リソースの部分更新。 PUTが全体置換なのに対し、PATCHは差分のみ送信。
DELETE
リソースの削除。 指定URIのリソースを削除する。 べき等
HEAD
GETと同じだがボディなし。 ヘッダー情報のみ取得。 ファイルサイズ確認などに使用。 べき等・安全
OPTIONS
サーバーが対応するメソッドを確認。 CORSプリフライトリクエストに使用。 べき等・安全
TRACE
リクエストのループバックテスト。 経路上のプロキシを確認するために使用。 セキュリティ上の理由で無効化されることが多い。
CONNECT
プロキシサーバーを通じたトンネル確立。 HTTPS通信のプロキシ経由接続に使用。

メソッドの性質

メソッド安全（副作用なし）べき等（何度実行しても同じ結果）ボディ
GET✅ 安全✅ べき等なし
HEAD✅ 安全✅ べき等なし
OPTIONS✅ 安全✅ べき等任意
PUT❌✅ べき等あり
DELETE❌✅ べき等任意
POST❌❌あり
PATCH❌❌（実装依存）あり

メソッド インタラクティブデモ

メソッドを選択すると、対応するリクエストメッセージの例を確認できます。

⚠️ GET と POST の主な違い
・GET：パラメータをURLに含める（クエリ文字列）。ブックマーク・キャッシュ可能。 ボディなし。べき等・安全
・POST：データをボディに含める。URLに表示されない。 キャッシュされない。べき等でない

⑤ HTTPのレスポンスメッセージ・ステータスコード

重要ポイント③：HTTPのレスポンスメッセージには、レスポンスの状態を3桁の数字で表したステータスコードが含まれる
HTTPレスポンスの先頭行（ステータスライン）には 3桁のステータスコードと理由フレーズが含まれます。 先頭の数字によって5つのクラスに分類されます。

ステータスコードの分類

1xx 情報
リクエストを受信中。処理継続を示す
2xx 成功
リクエストが正常に処理された
3xx リダイレクト
別のURLへの転送が必要
4xx クライアントエラー
クライアント側のリクエストに問題がある
5xx サーバーエラー
サーバー側で処理に失敗した

主要なステータスコード一覧

コードフレーズ説明
▼ 1xx 情報
100Continueリクエストの続きを送信してよい
101Switching Protocolsプロトコルを切り替える（WebSocketのUpgradeなど）
▼ 2xx 成功
200OKリクエスト成功。レスポンスボディにデータが含まれる
201Createdリソースの作成成功（POSTの結果など）
204No Content成功したがレスポンスボディなし（DELETEの結果など）
▼ 3xx リダイレクト
301Moved Permanently恒久的なリダイレクト。URLが永久に変更された
302Found一時的なリダイレクト

▼ 4xx クライアントエラー

403Forbiddenアクセス禁止（認証済みでも権限なし）

⑦ HTTPでの認証

主なHTTP認証方式

Basic認証
ユーザー名とパスワードをBase64エンコードして送信。 HTTPS必須（Base64は暗号化ではない）。 Authorization: Basic dXNlcjpwYXNz
Digest認証
パスワードをハッシュ化して送信。 Basic認証より安全だが、現在はBearerトークンが主流。
Bearer認証（トークン）
JWTなどのトークンをAuthorizationヘッダーで送信。 REST APIで最も広く使われる方式。 Authorization: Bearer eyJhbGci...
OAuth 2.0
第三者サービスへの認可を委譲する仕組み。 「Googleでログイン」などに使用。 アクセストークンを発行して利用。 
/* Basic認証のリクエスト例 */
GET /protected HTTP/1.1
Host:          api.example.com
Authorization: Basic dXNlcjpwYXNzd29yZA==
/* "user:password" を Base64 エンコードした値 */

/* Bearer認証（JWT）のリクエスト例 */
GET /api/users/me HTTP/1.1
Host:          api.example.com
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

/* 401 Unauthorized レスポンス（認証要求） */
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="api", charset="UTF-8"

⑧ HTTP Cookie（クッキー）

重要ポイント：CookieはHTTPのステートレスな性質を補い、セッション管理などに使われる
HTTPはステートレスなため、リクエストをまたいで状態を保持できません。 Cookie はサーバーが Set-Cookie ヘッダーでブラウザに保存させ、 以降のリクエストで自動的に Cookie ヘッダーとして送信される仕組みです。 セッション管理・ユーザー設定の保存・トラッキングなどに使われます。

Cookie の属性

属性説明
Expires / Max-Age有効期限。指定なしはセッションCookie（ブラウザを閉じると消える）
DomainCookieを送信するドメイン
PathCookieを送信するパス
SecureHTTPS接続時のみ送信される
HttpOnlyJavaScriptからアクセス不可（XSS対策）
SameSiteクロスサイトリクエストでの送信制御（CSRF対策）
Strict：同一サイトのみ / Lax：一部許可 / None：制限なし
 
/* サーバーからのSet-Cookieヘッダー */
HTTP/1.1 200 OK
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Strict; Max-Age=3600
Set-Cookie: theme=dark; Path=/; Max-Age=2592000

/* 以降のリクエストでは自動的にCookieが送信される */
GET /dashboard HTTP/1.1
Host:   www.example.com
Cookie: session=abc123; theme=dark

/* JavaScriptからのCookie操作（HttpOnlyでない場合のみ） */
document.cookie = "username=Alice; max-age=3600; path=/";
console.log(document.cookie); /* "username=Alice; theme=dark" */
⚠️ Cookie のセキュリティ
・HttpOnly：JavaScriptからのアクセスを禁止 → XSS攻撃でのCookie窃取を防ぐ
・Secure：HTTPS接続時のみ送信 → 通信経路での盗聴を防ぐ
・SameSite=Strict：クロスサイトリクエストでの送信を禁止 → CSRF攻撃を防ぐ

⑨ HTTP/2

重要ポイント①：HTTP/2はTCP接続を共有しリクエストを多重化するなど効率化を図っている
HTTP/2 は HTTP/1.1 の性能上の問題を解決するために策定されたバージョンです。 1つのTCP接続でリクエストを多重化（並列送受信）することで、 HTTP/1.1 で問題だった「Head-of-Line Blocking」を解消し、 Webページの読み込みを大幅に高速化します。

HTTP/1.1 vs HTTP/2 の主な違い

機能HTTP/1.1HTTP/2
TCP接続 リクエストごとに接続（または持続接続で順次処理） 1つのTCP接続を共有
多重化 不可（パイプライン化は問題あり） 複数リクエストを並列送受信（ストリーム）
ヘッダー圧縮 なし（毎回全ヘッダーを送信） HPACK圧縮（差分のみ送信）
サーバープッシュ なし サーバーが先読みしてリソースを送信可能
プロトコル形式 テキスト形式 バイナリ形式（フレーム単位）
優先度制御 なし ストリームに優先度を設定可能

HTTP/2 の多重化（Multiplexing）の仕組み

HTTP/1.1（順次処理）
リクエスト1
→
レスポンス1
→
リクエスト2
→
レスポンス2
HTTP/2（多重化）
1つのTCP接続上で複数のストリームが並列動作：
ストリーム1: ─── リクエスト1 ─── レスポンス1 ───
ストリーム2: ─── リクエスト2 ─── レスポンス2 ───
ストリーム3: ─── リクエスト3 ─── レスポンス3 ─── 
/* HTTP/2 はブラウザとサーバーが自動的にネゴシエーション */
/* 開発者が意識して書くコードはほぼ不要 */
/* ただし HTTPS（TLS）が実質的に必須 */

/* HTTP/2 の主な特徴 */
/* 1. 多重化（Multiplexing）：1つのTCP接続で複数リクエストを並列処理 */
/* 2. ヘッダー圧縮（HPACK）：重複ヘッダーを差分のみ送信 */
/* 3. サーバープッシュ：リクエスト前にサーバーがリソースを送信 */
/* 4. バイナリフレーム：テキストではなくバイナリ形式で効率的に転送 */
/* 5. ストリーム優先度：重要なリソースを優先して転送 */

/* Node.js での HTTP/2 サーバー例（概要） */
const http2 = require('http2');
const server = http2.createSecureServer({ key, cert });
server.on('stream', (stream, headers) => {
  stream.respond({ ':status': 200 });
  stream.end('Hello HTTP/2!');
});
✅ 試験でのポイント
・HTTP/2 は1つのTCP接続を共有し、リクエストを多重化する
・ヘッダー圧縮（HPACK）により毎回のヘッダー送信量を削減
・サーバープッシュでリクエスト前にリソースを先送りできる
・テキスト形式（HTTP/1.1）からバイナリ形式に変更
・実質的にHTTPS必須（主要ブラウザはHTTP/2をHTTPSのみで実装）
