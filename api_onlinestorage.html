① Web Storage

重要ポイント①：Web StorageやIndexed Databaseを用いて、ブラウザにデータを保存できる
Web Storage は localStorage（永続的保存）と sessionStorage（セッション中のみ保存）の2種類を提供します。 どちらもキーと値のペアで文字列データを保存します。 Cookieと異なり、サーバーには送信されず、より大きな容量（一般的に5MB程度）を利用できます。

localStorage vs sessionStorage vs Cookie の比較

項目localStoragesessionStorageCookie
保存期間 永続的（明示的に削除するまで） セッション中のみ（タブを閉じると消える） 有効期限を設定可能
スコープ 同一オリジン内で共有 同一タブ・同一オリジンのみ ドメイン・パスで制御
容量 約5MB（ブラウザ依存） 約5MB（ブラウザ依存） 約4KB
サーバー送信 送信されない 送信されない HTTPリクエストに自動付与
データ型 文字列のみ 文字列のみ 文字列のみ
JavaScript API localStorage sessionStorage document.cookie

Web Storage の主なメソッド・プロパティ

setItem(key, value)
キーと値を保存する。既存のキーは上書きされる
getItem(key)
キーに対応する値を取得する。存在しない場合は null を返す
removeItem(key)
指定したキーのデータを削除する
clear()
すべてのデータを削除する
key(index)
インデックスに対応するキー名を返す
length
保存されているデータの件数を返す
/* localStorage：永続的に保存（タブを閉じても残る） */
localStorage.setItem('username', 'Alice');       /* 保存 */
const name = localStorage.getItem('username');    /* 取得 → 'Alice' */
localStorage.removeItem('username');             /* 削除 */
localStorage.clear();                             /* 全削除 */

/* オブジェクトを保存する場合はJSON文字列に変換する */
const user = { name: 'Alice', age: 30 };
localStorage.setItem('user', JSON.stringify(user));   /* 保存 */
const saved = JSON.parse(localStorage.getItem('user')); /* 取得・復元 */

/* sessionStorage：タブを閉じると消える */
sessionStorage.setItem('token', 'abc123');
const token = sessionStorage.getItem('token');

/* storage イベント：他のタブでの変更を検知（localStorageのみ） */
window.addEventListener('storage', (e) => {
  console.log('変更されたキー:', e.key);
  console.log('変更前の値:',   e.oldValue);
  console.log('変更後の値:',   e.newValue);
});

② Indexed Database API（IndexedDB）

重要ポイント①（続き）：IndexedDatabaseを用いて、ブラウザに大量の構造化データを保存できる
IndexedDB はブラウザ内蔵のNoSQL型データベースです。 Web Storage と異なり、オブジェクト・バイナリデータをそのまま保存でき、 インデックスを使った高速な検索も可能です。 大容量データ（数百MB以上）の保存に適しています。 すべての操作は非同期（トランザクション）で行われます。

Web Storage vs IndexedDB の比較

項目Web StorageIndexedDB
データ型文字列のみオブジェクト・バイナリも可
容量約5MB大容量（数百MB以上）
検索キーのみインデックスによる高速検索
操作方式同期（シンプル）非同期（トランザクション）
構造キー・バリューのみデータベース → オブジェクトストア → レコード
向いている用途設定・トークンなど小さなデータ大量データ・オフラインアプリ

/* IndexedDB のオープン（バージョン管理あり） */
const request = indexedDB.open('myDatabase', 1); /* DB名, バージョン */

/* onupgradeneeded：DB作成・バージョンアップ時に呼ばれる */
request.onupgradeneeded = (event) => {
  const db    = event.target.result;
  /* オブジェクトストア（テーブル相当）を作成 */
  const store = db.createObjectStore('users', { keyPath: 'id' });
  /* インデックスを作成（nameプロパティで検索可能に） */
  store.createIndex('name', 'name', { unique: false });
};

/* onsuccess：DB接続成功 */
request.onsuccess = (event) => {
  const db = event.target.result;

  /* データの追加（readwriteトランザクション） */
  const tx    = db.transaction('users', 'readwrite');
  const store = tx.objectStore('users');
  store.add({ id: 1, name: 'Alice', age: 30 });

  /* データの取得（readトランザクション） */
  const tx2    = db.transaction('users', 'readonly');
  const store2 = tx2.objectStore('users');
  const getReq = store2.get(1); /* id=1 のレコードを取得 */
  getReq.onsuccess = () => console.log(getReq.result);

  /* インデックスを使った検索 */
  const index   = store2.index('name');
  const idxReq  = index.get('Alice');
  idxReq.onsuccess = () => console.log(idxReq.result);
};

request.onerror = (event) => console.log('エラー:', event.target.error);

③ Web Workers

重要ポイント②：Web Workerを用いて、JavaScriptで並列処理を行える
JavaScriptはシングルスレッドで動作するため、重い処理を実行するとUIがフリーズします。 Web Workers を使うと、メインスレッドとは別のバックグラウンドスレッドで JavaScriptを実行でき、UIをブロックせずに並列処理が可能になります。 メインスレッドとWorkerは postMessage() と onmessage で通信します。

Web Workers の通信モデル

メインスレッド（UI）
DOM操作・イベント処理を担当
待機中...
postMessage() → ← onmessage
Worker スレッド
重い処理をバックグラウンドで実行
待機中...
/* ===== メインスレッド側（main.js） ===== */

/* Workerの作成（別ファイルを指定） */
const worker = new Worker('worker.js');

/* Workerにメッセージを送信 */
worker.postMessage({ type: 'calc', data: 1000000 });

/* Workerからのメッセージを受信 */
worker.onmessage = (event) => {
  console.log('Worker結果:', event.data);
};

/* エラーハンドリング */
worker.onerror = (error) => {
  console.log('Workerエラー:', error.message);
};

/* Workerの終了 */
worker.terminate();


/* ===== Workerスレッド側（worker.js） ===== */

/* メインスレッドからのメッセージを受信 */
self.onmessage = (event) => {
  const { type, data } = event.data;

  if (type === 'calc') {
    /* 重い処理（例：大量の計算） */
    let result = 0;
    for (let i = 0; i < data; i++) result += i;

    /* 結果をメインスレッドに返す */
    self.postMessage({ type: 'result', result });
  }
};

Web Workers の種類

種類説明特徴
Dedicated Worker 特定のスクリプトに紐付いた専用Worker 最も一般的。new Worker('worker.js') で作成
Shared Worker 複数のタブ・ウィンドウで共有できるWorker new SharedWorker('worker.js') で作成。port 経由で通信

⚠️ Web Workers の制約
・DOMへのアクセスは不可です（document・window は使えない）
・メインスレッドとのデータのやり取りは postMessage() / onmessage を通じて行います
・渡されるデータはコピー（構造化クローン）されます（参照は共有されない）
・XMLHttpRequest・fetch・setTimeout などは利用可能です

④ Service Workers

重要ポイント③（前半）：Service Workersはブラウザとネットワークの間に立つプロキシとして動作する
Service Worker はブラウザのバックグラウンドで動作する特殊なWorkerです。 Webページとは独立して動作し、ネットワークリクエストの傍受・キャッシュ制御・ オフライン対応・プッシュ通知などを実現します。 HTTPS（セキュアコンテキスト）でのみ動作します。

Service Worker の主なイベント

activateService Worker の有効化時古いキャッシュの削除

/* ===== メインスレッド：Service Worker の登録 ===== */
if ('serviceWorker' in navigator) {
  navigator.serviceWorker.register('/sw.js')
    .then(reg => console.log('SW登録成功:', reg.scope))
    .catch(err => console.log('SW登録失敗:', err));
}


/* ===== sw.js：Service Worker 本体 ===== */
const CACHE_NAME = 'my-cache-v1';
const CACHE_URLS = ['/', '/index.html', '/style.css', '/app.js'];

/* install：静的リソースをキャッシュ */
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open(CACHE_NAME)
      .then(cache => cache.addAll(CACHE_URLS))
  );
});

/* activate：古いキャッシュを削除 */
self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then(keys =>
      Promise.all(
        keys.filter(k => k !== CACHE_NAME)
            .map(k => caches.delete(k))
      )
    )
  );
});

/* fetch：キャッシュ優先で応答（オフライン対応） */
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request)
      .then(cached => cached || fetch(event.request))
  );
});
✅ 試験でのポイント
・Service Worker はHTTPS必須（localhost は例外）
・ライフサイクルは register → install → activate → fetch/push の順
・fetch イベントでリクエストを傍受し、キャッシュからの応答でオフライン対応できる
・DOMへのアクセスは不可（Web Workerと同様）

⑤ Push API

重要ポイント③：Service WorkersのPush APIとfetchを組み合わせ、ブラウザでプッシュ通知およびメッセージ本体を受信できる
Push API は Service Worker と組み合わせて、 ブラウザが閉じていても・Webページを開いていなくても サーバーからのプッシュ通知を受信できるAPIです。 通知の受信は Service Worker の push イベントで処理し、 Fetch API を使ってメッセージの本文をサーバーから取得します。

/* ===== メインスレッド：プッシュ通知の購読 ===== */

/* Step 1：通知の許可を要求 */
const permission = await Notification.requestPermission();
if (permission !== 'granted') return;

/* Step 2：Service Worker の登録を取得 */
const reg = await navigator.serviceWorker.ready;

/* Step 3：プッシュ通知を購読 */
const subscription = await reg.pushManager.subscribe({
  userVisibleOnly: true,       /* 必須：ユーザーに見える通知のみ */
  applicationServerKey: vapidPublicKey /* VAPIDキー（サーバー認証用） */
});

/* Step 4：購読情報（エンドポイントURL）をサーバーに送信 */
await fetch('/subscribe', {
  method: 'POST',
  body:   JSON.stringify(subscription),
  headers: { 'Content-Type': 'application/json' }
});


/* ===== sw.js：プッシュ通知の受信と表示 ===== */

/* push イベント：サーバーからプッシュ通知を受信 */
self.addEventListener('push', (event) => {
  /* Fetch APIでメッセージ本文をサーバーから取得 */
  event.waitUntil(
    fetch('/push-message')
      .then(res => res.json())
      .then(data => {
        /* 通知を表示 */
        return self.registration.showNotification(data.title, {
          body:  data.body,
          icon:  data.icon,
          badge: data.badge
        });
      })
  );
});

/* notificationclick：通知クリック時の処理 */
self.addEventListener('notificationclick', (event) => {
  event.notification.close();
  event.waitUntil(clients.openWindow('/'));
});

Push API と Fetch API の連携ポイント

役割API説明
通知の受信 Push API（push イベント） Service Worker がサーバーからのプッシュを受け取る
本文の取得 Fetch API（fetch()） push イベント内で fetch を使い、通知の詳細データをサーバーから取得する
通知の表示 Notifications API（showNotification()） 取得したデータをもとに通知を表示する
購読管理 PushManager（pushManager.subscribe()） ブラウザをプッシュ通知に購読登録する
⚠️ Push API の注意点
・HTTPS必須（Service Worker が必要なため）
・userVisibleOnly: true は必須です（サイレントプッシュは許可されていない）
・VAPID（Voluntary Application Server Identification）キーによるサーバー認証が必要です
・push イベント内で event.waitUntil() を使い、処理が完了するまでService Workerを維持します

⑥ Fetch API

重要ポイント③（続き）：Fetch APIはPromiseベースのHTTPリクエストAPIで、Service Worker内でも利用できる
Fetch API は XMLHttpRequest（XHR）の後継となる、 PromiseベースのモダンなネットワークリクエストAPIです。 シンプルな記述でHTTPリクエストを送受信でき、 Service Worker内でも利用可能なため、 Push API との連携でメッセージ本文の取得に使われます。

XHR vs Fetch API の比較

項目XMLHttpRequest（XHR）Fetch API
記述スタイルコールバックベースPromiseベース（async/await対応）
可読性コールバックが深くなりがちシンプルで読みやすい
Service Worker利用不可利用可能
ストリーミング限定的ReadableStream で対応
進捗取得対応（onprogress）限定的（ReadableStreamで可能）
エラー処理onerror コールバック.catch() / try-catch
 
/* 基本的な GET リクエスト */
fetch('https://api.example.com/data')
  .then(response => {
    /* HTTPステータスの確認 */
    if (!response.ok) {
      throw new Error(`HTTP error: ${response.status}`);
    }
    return response.json(); /* JSONとして解析 */
  })
  .then(data => console.log(data))
  .catch(err => console.log('エラー:', err));


/* async/await を使った記述（より読みやすい） */
async function fetchData() {
  try {
    const response = await fetch('https://api.example.com/data');
    if (!response.ok) throw new Error(`${response.status}`);
    const data = await response.json();
    console.log(data);
  } catch (err) {
    console.log('エラー:', err);
  }
}


/* POST リクエスト（オプション指定） */
fetch('https://api.example.com/users', {
  method:  'POST',
  headers: { 'Content-Type': 'application/json' },
  body:    JSON.stringify({ name: 'Alice', age: 30 })
});


/* Response オブジェクトの主なメソッド */
response.json();    /* JSONとして解析 → Promise<any> */
response.text();    /* テキストとして取得 → Promise<string> */
response.blob();    /* Blobとして取得（画像など） → Promise<Blob> */
response.arrayBuffer(); /* ArrayBufferとして取得 → Promise<ArrayBuffer> */
response.ok;        /* ステータスが200〜299かどうか（boolean） */
response.status;    /* HTTPステータスコード（例: 200, 404） */
response.headers;   /* レスポンスヘッダー（Headers オブジェクト） */
